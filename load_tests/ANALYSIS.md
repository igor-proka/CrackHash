# Подробный анализ нагрузочных тестов CrackHash

> Этот файл описывает legacy Java-нагрузочный тест из Task 1 и оставлен как исторический baseline.
> Для текущей Task 2 основным сценарием является `load_tests/k6/crackhash.js`, а результаты смотрятся через Prometheus/Grafana.

## 1. Как работает нагрузочный тест

### 1.1 Что делает тестовый скрипт (`LoadTest.java`)

Скрипт использует встроенный в Java 11 асинхронный HTTP-клиент (`java.net.http.HttpClient`).

**Алгоритм работы:**
1. Создается один экземпляр `HttpClient` (пул соединений общий для всех клиентов).
2. В цикле создается N объектов `CompletableFuture` — каждый из них представляет одного "виртуального клиента".
3. Каждый клиент отправляет **асинхронный** POST-запрос на эндпоинт Менеджера `/api/hash/crack` с JSON-телом:
   ```json
   {"hash": "098f6bcd4621d373cade4e832627b4f6", "maxLength": 4}
   ```
   Это MD5 хэш от слова `"test"`, длина ≤ 4.
4. Все запросы отправляются **одновременно** (не последовательно) — именно это создает нагрузку.
5. Для каждого запроса фиксируется результат: успех, таймаут, отказ в соединении и т.д.
6. В конце подсчитывается общая статистика.

### 1.2 Что происходит на стороне Менеджера при получении запроса

Когда POST-запрос от клиента приходит на Менеджер, он проходит следующий путь:

```
Клиент (LoadTest)
   │
   │  HTTP POST /api/hash/crack
   ▼
┌──────────────────────────────┐
│  Embedded Tomcat (port 8082) │
│  ┌────────────────────────┐  │
│  │  Thread Pool (200 пот.)│  │  ← Пул рабочих потоков Tomcat
│  │  + Backlog (100 сокет.)│  │  ← TCP-очередь ожидания
│  └────────────────────────┘  │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│  ClientApi.crackHash()       │  ← REST-контроллер (аннотация @PostMapping)
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│  ManagerService              │
│  .createCrackTask()          │  ← Генерирует UUID, сохраняет TaskState
│                              │     в ConcurrentHashMap, запускает
│                              │     отдельный поток для рассылки
│                              │     задач 3-м воркерам
└──────────────────────────────┘
```

#### Что такое Tomcat и почему он ограничивает нагрузку

**Apache Tomcat** — это встроенный HTTP-сервер, который Spring Boot использует для обслуживания HTTP-запросов. В нашем проекте он запускается автоматически при старте `ManagerApplication`.

Tomcat работает по модели **"один поток на один запрос"** (Blocking I/O):
- Для каждого входящего HTTP-запроса Tomcat выделяет один поток из пула.
- Поток занят, пока запрос полностью не обработан и ответ не отправлен клиенту.
- По умолчанию в Spring Boot размер пула = **200 потоков**.

Помимо пула потоков, у Tomcat есть **TCP backlog** — это очередь на уровне операционной системы, куда попадают TCP-соединения, которые уже установлены, но ещё не назначены рабочему потоку. По умолчанию backlog = **100**.

**Итого Tomcat может "держать" одновременно:**
- 200 запросов в обработке (в потоках)
- ~100 запросов в очереди ожидания (TCP backlog)
- **≈ 300 одновременных соединений максимум**

Всё, что приходит сверх этого, получает **отказ на уровне TCP** — операционная система возвращает `Connection Refused`, даже не доходя до Java-кода.

Эти параметры задаются в конфигурации Spring Boot:
```yaml
server:
  tomcat:
    threads:
      max: 200       # макс. количество потоков (по умолчанию)
    accept-count: 100 # TCP backlog (по умолчанию)
```

В нашем файле `manager/src/main/resources/application.yml` мы **не переопределяли** эти значения, поэтому используются значения по умолчанию.

### 1.3 Что происходит на стороне Воркеров

Когда Менеджер принимает запрос, он в отдельном потоке (`new Thread(...)`) рассылает задачи 3-м воркерам. Каждый воркер:

1. Принимает задачу в контроллере `WorkerApi.receiveTask()`.
2. Отправляет задачу в `ExecutorService` с пулом **4 потока** (`Executors.newFixedThreadPool(4)`).
3. `ExecutorService` использует **бесконечную очередь** (`LinkedBlockingQueue` — она не имеет лимита!).
4. Если задач приходит больше, чем 4 потока успевают обработать, они копятся в этой очереди.

**Проблема:** При 10 000 запросов от клиентов, Менеджер посылает ~3000×N задач воркерам. Каждая задача содержит объект `WorkerTaskRequest` + контекст потока. При огромном потоке задач очередь разрастается и может привести к `OutOfMemoryError` (исчерпание Java Heap).

```
Менеджер
   │
   │  HTTP POST (×3 на каждый запрос — по одному на воркер)
   ▼
┌─────────────────────────────────┐
│  Worker Tomcat (port 8081)      │
│  ┌───────────────────────────┐  │
│  │ WorkerApi.receiveTask()   │  │
│  │         │                 │  │
│  │         ▼                 │  │
│  │ ExecutorService           │  │
│  │ ┌─────────────────────┐   │  │
│  │ │ Thread 1 │ Thread 2 │   │  │  ← 4 рабочих потока
│  │ │ Thread 3 │ Thread 4 │   │  │
│  │ └─────────────────────┘   │  │
│  │ LinkedBlockingQueue: ∞    │  │  ← БЕСКОНЕЧНАЯ очередь!
│  │ [Task][Task][Task][Task]  │  │
│  │ [Task][Task][Task]...     │  │  ← При перегрузке — OutOfMemory
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

## 2. Классификация результатов теста

Скрипт классифицирует результаты в 4 категории:

### SUCCESS (200)
Менеджер успешно принял запрос: Tomcat выделил поток → `ClientApi.crackHash()` вызван → `ManagerService.createCrackTask()` создал `TaskState` в `ConcurrentHashMap` → вернул `requestId` клиенту.

### TIMEOUT
TCP-соединение с сервером **установлено**, но Menеджер **не успел ответить** в течение 10 секунд (`REQUEST_TIMEOUT`). Это означает, что запрос попал в TCP backlog или в очередь обработки Tomcat, но все 200 потоков заняты другими запросами, и до этого запроса очередь не дошла.

### CONNECTION_REFUSED
Операционная система контейнера **отклонила TCP-соединение** ещё до того, как оно дошло до Tomcat. Это происходит, когда:
- Все 200 потоков Tomcat заняты.
- TCP backlog (100 соединений) тоже заполнен.
- ОС больше не может принимать новые соединения и возвращает `RST`-пакет.

Это самый "тяжелый" вид отказа — клиент даже не смог установить TCP-соединение.

### CONNECTION_RESET
TCP-соединение было **установлено**, но затем **разорвано** сервером (TCP RST). Это может происходить когда:
- Tomcat принял соединение, но затем закрыл его из-за перегрузки.
- JVM испытывает проблемы с памятью и сбрасывает соединения.

## 3. Результаты тестирования

### Тест №1: 1 000 клиентов
```
Total time: 4.61 sec
Total requests: 1000
RPS: 216.87

Results:
  SUCCESS (200)                  :   974 (97.4%)
  CONNECTION_REFUSED (Tomcat)    :    26 (2.6%)
```
**Вывод:** Даже при 1000 запросах мы увидели первые признаки деградации (2.6% отказов).

---

### Тест №2: 10 000 клиентов
```
Total time: 18.05 sec
Total requests: 10000
RPS: 554.17

Results:
  TIMEOUT (сервер не успел ответить) :  5317 (53.2%)
  SUCCESS (200)                      :  3215 (32.2%)
  CONNECTION_REFUSED (Tomcat перегруж.):  1193 (11.9%)
  CONNECTION_RESET (соединение разорв.):   275 (2.8%)
```
**Вывод:** Система начинает **явно деградировать**:
- Только 32% запросов обработаны успешно.
- 53% зависли в ожидании (TIMEOUT) — Tomcat принял TCP-соединение, но потоков не хватило.
- 12% получили жесткий отказ (CONNECTION_REFUSED) — TCP backlog переполнен.
- 2.8% были принятых и затем разорваны (CONNECTION_RESET) — сервер не выдержал.

---

### Тест №3: 100 000 клиентов
```
Total time: 40.72 sec
Total requests: 100000
RPS: 2455.68

Results:
  CONNECTION_REFUSED (Tomcat перегруж.): 83778 (83.8%)
  TIMEOUT (сервер не успел ответить)  : 15153 (15.2%)
  SUCCESS (200)                       :  1069 (1.1%)
```
**Вывод:** Система **практически неработоспособна**:
- Лишь 1.1% запросов обработаны — это примерно 1069 задач.
- 83.8% отброшены ОС ещё на уровне TCP — Tomcat физически не может принять столько соединений.
- Реальный полезный RPS ≈ 1069 / 40.7 ≈ **~26 запросов/сек** (остальные мгновенно отбиты с ошибкой).
