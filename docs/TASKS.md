## Предисловие

Требуется реализовать распределенную систему для взлома хэша под кодовым именем **CrackHash**.

Непосредственный взлом хэша выполняется простым перебором словаря, сгенерированного на основе заданного алфавита, то есть brute-force.

Общая логика системы:

1. Менеджер принимает от пользователя запрос, содержащий MD5-хэш некоторого слова и максимальную длину исходного слова.
2. Менеджер обрабатывает запрос: генерирует задачи на перебор слов, составленных из переданного алфавита, и распределяет их между воркерами.
3. Каждый воркер принимает задачу, перебирает слова в своем диапазоне и вычисляет их хэш.
4. Если воркер находит слово с совпадающим хэшем, он возвращает результат менеджеру.

## Task 1: Services Implementation

В рамках первой лабораторной работы необходимо реализовать приложения **manager** и **worker**, а также организовать простое взаимодействие между ними через HTTP.

Очереди, producer-ы и listener-ы в рамках этой задачи настраивать не требуется.

### Общие требования к сервисам

- Приложения должны быть реализованы на **Java 11+** с использованием **Spring Boot**.
- Для сборки рекомендуется использовать **Gradle 6+**.
- Для развертывания сервисов необходимо использовать **Docker Compose**.
- Конфигурация Docker Compose должна содержать одного воркера.
- Запросы между менеджером и воркером должны передаваться внутри сети Docker Compose по HTTP.
- В качестве доменов для межсервисного взаимодействия должны использоваться имена сервисов из Docker Compose.

### Требования к manager

Manager должен предоставлять клиенту REST API в формате JSON.

Запрос на взлом хэша, например для слова `abcd`:

```http
POST /api/hash/crack
```

Request body:

```json
{
  "hash": "e2fc714c4727ee9395f324cd2e7f331f",
  "maxLength": 4
}
```

В ответ manager должен вернуть идентификатор запроса, по которому клиент сможет получить результат:

```json
{
  "requestId": "730a04e6-4de9-41f9-9d5b-53b88b17afac"
}
```

Для получения результата manager должен предоставлять API:

```http
GET /api/hash/status?requestId=730a04e6-4de9-41f9-9d5b-53b88b17afac
```

Ответ, если запрос еще обрабатывается:

```json
{
  "status": "IN_PROGRESS",
  "data": null
}
```

Ответ, если результат готов:

```json
{
  "status": "READY",
  "data": ["abcd"]
}
```

Дополнительные требования к manager:

- В качестве алфавита должны использоваться строчные латинские буквы и цифры.
- Взаимодействие между manager и worker должно быть организовано в формате JSON.
- Необходимо сгенерировать модель запроса manager к worker на основе XSD-схемы.
- Запросы для worker должны заполняться в соответствии со сгенерированной моделью.
- Перед отправкой задач worker-ам manager должен сохранить в оперативной памяти информацию о задачах с привязкой к клиентскому запросу.
- Запрос должен сохраняться в статусе `IN_PROGRESS` под идентификатором, который выдается пользователю.
- После получения ответов от всех worker-ов manager должен перевести статус запроса в `READY`.
- По истечении таймаута запрос должен перейти в статус `ERROR`.
- Для хранения состояния запросов необходимо использовать потокобезопасные коллекции.
- Взаимодействие с worker нужно организовать по HTTP с помощью `RestTemplate`.

Worker должен реализовать контроллер для обработки запросов от manager:

```http
POST /internal/api/worker/hash/crack/task
```

### Требования к worker

- Взаимодействие между worker и manager также должно быть организовано в формате XML.
- Необходимо сгенерировать модель ответа worker на основе XSD-схемы.
- Ответ для manager должен заполняться в соответствии со сгенерированной моделью.
- Взаимодействие с manager нужно организовать по HTTP с помощью `RestTemplate`.

Manager должен реализовать контроллер для обработки ответов от worker:

```http
PATCH /internal/api/manager/hash/crack/request
```

### Генерация и распределение слов

Для генерации слов на основе полученного алфавита можно использовать библиотеку `combinatoricslib3`.

Библиотека позволяет генерировать перестановки с повторениями заданной длины на основе заданного множества. Важное условие: worker не должен держать в памяти все сгенерированные комбинации, потому что при увеличении максимальной длины последовательностей их становится слишком много.

Для этого библиотека предоставляет итератор по множеству комбинаций.

Расчет диапазона слов необходимо производить на основе значений `PartNumber` и `PartCount` из запроса от manager. Все пространство слов должно быть поделено поровну между worker-ами.

## Task 2: Fault Tolerance

В рамках второй лабораторной работы необходимо модифицировать систему так, чтобы обеспечить гарантированную обработку запроса пользователя, если доступен manager. То есть требуется обеспечить отказоустойчивость системы в целом.

### Основные требования

#### Сохранность данных при отказе manager

- Необходимо обеспечить хранение данных об обрабатываемых запросах в базе данных.
- Необходимо организовать взаимодействие worker-ов с manager через очередь RabbitMQ.
- Достаточно настроить очередь с `direct exchange`.
- Если manager недоступен, сообщения должны сохраняться в очереди до момента возобновления его работы.
- RabbitMQ необходимо разместить в окружении Docker Compose.

#### Частичная отказоустойчивость базы данных

- База данных также должна быть отказоустойчивой.
- Требуется реализовать простое реплицирование для нереляционной базы MongoDB.
- Минимально рабочая схема: одна `primary`-нода и две `secondary`-ноды.
- Manager должен отвечать клиенту, что задача принята в работу, только после успешного сохранения данных в базу и их репликации.

#### Сохранность данных при отказе worker-ов

- В Docker Compose необходимо разместить как минимум двух worker-ов.
- Взаимодействие manager с worker-ами нужно организовать через RabbitMQ.
- Для этого требуется вторая отдельная очередь, также с `direct exchange`.
- Если один из worker-ов во время работы над задачей ломается и не отдает ответ, задача должна быть переотправлена другому worker-у.
- Для переотправки задачи необходимо корректно настроить механизм acknowledgement-ов.
- Если на момент создания задач нет доступных worker-ов, сообщения должны дождаться их появления в очереди и затем отправиться на исполнение.

#### Сохранность данных при отказе RabbitMQ

- Если manager не может отправить задачи в очередь, он должен сохранить их у себя в базе данных до момента восстановления доступности очереди.
- После восстановления RabbitMQ manager должен снова отправить накопившиеся задачи.
- Очередь не должна терять сообщения при рестарте или падении из-за ошибки.
- Для этого все сообщения должны быть персистентными.

### Проверяемые сценарии отказов

#### Остановка manager в Docker Compose

Ожидаемое поведение:

- полученные ранее ответы от worker-ов должны быть сохранены в базу и не должны потеряться;
- ответы на задачи, которые не дошли до manager, не должны потеряться;
- после рестарта manager должен подобрать такие ответы из очереди.

#### Остановка primary-ноды MongoDB replica set

Ожидаемое поведение:

- `primary`-нода должна измениться;
- система должна продолжить работу в штатном режиме.

#### Остановка RabbitMQ в Docker Compose

Ожидаемое поведение:

- все необработанные на момент выключения очереди сообщения не должны потеряться;
- после рестарта RabbitMQ сообщения должны остаться доступными для обработки.

#### Остановка worker во время обработки задачи

Ожидаемое поведение:

- сообщение должно быть переотправлено другому worker-у;
- задача не должна потеряться.

### Примечания из задания

- Для отправки и получения XML-сообщений через очередь рекомендуется использовать `MarshallingMessageConverter` и `Jaxb2Marshaller` в связке с `AmqpTemplate` для отправки и `@RabbitListener` для получения.
- При рестарте RabbitMQ сбрасывает статус персистентных отправленных сообщений из `unacked` в `ready`.
- Поэтому допускается повторная обработка одной задачи двумя worker-ами. Это необходимо учитывать в логике manager.

## Как текущая реализация закрывает Task 2

- Состояние запросов хранится в MongoDB replica set.
- Manager использует сохранение с `writeConcern=majority`.
- Части задач сохраняются в MongoDB как outbox-записи.
- RabbitMQ использует durable direct exchanges и durable queues.
- Сообщения задач и результатов отправляются как persistent messages.
- Для публикации используются publisher confirms.
- Manager и worker используют manual acknowledgements.
- При недоступности RabbitMQ части остаются в статусах `PENDING_PUBLISH` или `PUBLISH_FAILED`.
- Результаты обрабатываются идемпотентно по паре `requestId + partNumber`.
- Наблюдаемость обеспечивают Prometheus, Grafana, Spring Boot Actuator и k6.
