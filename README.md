# CrackHash
Данный репозиторий посвящен лабам курса "Распределенные информационные системы". НГУ ФИТ 4 курс. 2026

## Описание архитектуры и работы системы (Task 1)

Система **CrackHash** состоит из трех основных компонентов:
1. **Manager (Менеджер)** — оркестратор (Spring Boot). Принимает запросы от клиентского приложения, разбивает задачу на 3 части (по количеству воркеров) и асинхронно раздает им эти части по HTTP. Хранит состояние всех задач в потокобезопасной памяти (`ConcurrentHashMap`). Периодически (каждые 10 секунд) проверяет таймауты и переводит просроченные задачи в статус `ERROR`.
2. **Worker (Воркер)** — вычислительный узел (Spring Boot). Выделено 3 уникальных контейнера. Получает свою часть работы, генерирует перестановки алфавита заданной длины (используя встроенную библиотеку `combinatoricslib3`), вычисляет от них MD5-хэш и сравнивает с искомым. Найденные совпадения асинхронно отправляет обратно Менеджеру.
3. **Client (Клиент)** — веб-интерфейс на React (Vite). Позволяет отправлять запросы на взлом, просматривать историю (которая бережно сохраняется в `localStorage`), отслеживать статусы (через фоновый поллинг каждые 2 секунды) и локально генерировать MD5-хэши для тестов. Поддерживает переключение светлой и темной темы.

Все сервисы упакованы в Docker-контейнеры и объединены в `docker-compose.yml` в изолированной сети.

## Как запустить систему

Для запуска всей инфраструктуры (Менеджер, 3 Воркера, Клиент) вам понадобится установленный **Docker** и **Docker Compose**.

1. **Клонируйте репозиторий** (если вы еще не там).
2. **Соберите и запустите контейнеры**:
   ```bash
   docker-compose up --build -d
   ```
3. **Откройте веб-интерфейс**:
   - Клиент доступен по адресу: [http://localhost](http://localhost)
   - API Менеджера (для прямых запросов): [http://localhost:8080](http://localhost:8080)

Чтобы остановить систему:
```bash
docker-compose down
```

## Основные выполненные требования к системе (пока по Task 1)

Ниже разобраны все требования изначального ТЗ и то, как они интегрированы в код:

### 1. Передача запроса от клиента менеджеру
> *Менеджер принимает от пользователя запрос (MD-5 хэш и максимальную длину) по POST `/api/hash/crack` и отдает `requestId`.*
✅ **Выполнено:** Реализовано в `manager/.../controller/ClientApi.java`. REST-эндпоинт принимает JSON на вход и мгновенно возвращает UUID, не дожидаясь расчетов (асинхронность).

### 2. Генерация и распределение задач воркерам
> *Менеджер генерирует задачи в соответствии с заданным числом воркеров и отправляет их на исполнение.*
✅ **Выполнено:** В `docker-compose.yml` запущены 3 именованных контейнера: `worker-1`, `worker-2`, `worker-3`. В конфиге `application.yml` Менеджера переданы эти 3 адреса. При поступлении запроса, `ManagerService.java` делит работу на `partCount = 3` и отправляет каждому воркеру уникальный `partNumber`.

### 3. Обработка задачи воркером
> *Воркер перебирает слова в заданном диапазоне, вычисляет хэш, и если совпадает — возвращает менеджеру.*
✅ **Выполнено:** Контроллер `WorkerApi` принимает таску и отдаёт её во встроенный `ExecutorService` (пул потоков), чтобы сразу ответить HTTP 200 менеджеру, а вычисления запустить в фоне. Метод `HashCracker.crack()` выполняет перебор. Итоги запаковываются в `WorkerResponse` и "улетают" обратно Менеджеру.

### 4. Взаимодействие без очередей по HTTP (REST)
> *Настройка очередей не предполагается, всё по HTTP.*
✅ **Выполнено:** Коммуникация строгая "точка-точка". Менеджер делает POST-запрос, Воркер отвечает ему через PATCH на `/internal/api/manager/hash/crack/request`. Используется Spring `RestTemplate` (к которому мы прикрутили Apache HttpClient, чтобы `PATCH` работал корректно).

### 5. Технический стек (Java 11+, Spring Boot, Gradle, Docker Compose)
> *Запросы внутри сети docker-compose по доменам-именам сервисов.*
✅ **Выполнено:** Папки проектов инициализированы на Java 11 (через Temurin 11 JDK). Описаны двухэтапные сборки `Dockerfile` на базе Alpine, а в docker-compose Менеджер обращается к воркерам напрямую по их DNS-именам (например, `http://worker-2:8081`).

### 6. Получение статуса задачи клиентом
> *GET `/api/hash/status?requestId=...` возвращает `IN_PROGRESS` или `READY` с массивом данных.*
✅ **Выполнено:** Эндпоинт реализован. Ответ также сериализуется в JSON. Клиент вызывает этот метод каждые 2 секунды.

### 7. Применение JSON (вместо XML) и алфавит
> *Взаимодействие должно быть в JSON (по вашей просьбе вместо XML), алфавит: строчные буквы и цифры.*
✅ **Выполнено:** Алфавит строго зафиксирован (`abcdefghijklmnopqrstuvwxyz0123456789`). Огромный плюс JSON — мы избавились от генерации гигантских JAXB/XSD моделей. Используются компактные DTO классы на Lombok. Весь обмен работает с типом `application/json`.

### 8. Менеджер: Хранение состояния и таймауты
> *Менеджер должен сохранить информацию с привязкой к запросу в статусе IN_PROGRESS... Использовать потокобезопасные коллекции... По истечении таймаута запрос перевести в ERROR.*
✅ **Выполнено:** 
- Паттерн "Репозиторий" -> реализован класс `InMemoryTaskRepository`, прячущий в себе `ConcurrentHashMap`. 
- Проблема *Race Conditions* (состояния гонки, когда ответы от 3-х воркеров приходят одновременно в один миллисекундный промежуток) решена синхронизированным доступом к записи (`synchronized (state)` блока в `ManagerService`).
- Таймауты реализованы через `@Scheduled` джобу, которая сканирует старые задачи каждые 10 секунд, по умолчанию таймаут - 5 минут.

### 9. Воркер: Вычисления
> *Генерация слов через combinatoricslib3, итератор по множеству, чтобы не держать все в памяти.*
✅ **Выполнено:** Используется класс `Generator.permutation()`. Фишка в том, что мы не создаем список, а берем `stream()`. Высчитываем `startIdx` и `endIdx` для каждого воркера на основе математики длины алфавита. Вызывая `.skip(startIdx).limit(chunkSize)::iterator`, воркер не выделяет ОЗУ под миллионы вариантов, а генерирует лишь свой доверенный ему кусочек слов "на лету".

### 10. Качество кода (SOLID и ООП паттерны)
> *Код должен быть написан с использованием подходящих паттернов, принципов ООП, SOLID.*
✅ **Выполнено:**
- **S (Single Responsibility Principle):** Жесткое деление по слоям. Controller только для валидации и HTTP, Service только для бизнес-логики (комбинаторика, дробление задач), Repository только для хранения.
- **О и D (Open/Closed & Dependency Inversion Principle):** Для взлома (комбинаторики) заведен интерфейс `HashCracker`. Менеджеру внедряется он, а не конкретный класс. Если в Task 2 понадобится другой алгоритм взлома — пишется новая имплементация, а старый код не ломается.
- **IoC-контейнеры (Inversion of Control):** `RestTemplate` создается в конфигурационных классах (`AppConfig`), навешивается кастомная фабрика (Apache HTTP), и бин `RestTemplate` инжектится через Spring DI. Захардкоженных `new RestTemplate()` прямо в коде нет.

### 11. React-клиент и доп. функционал
> *Клиент на React веб, поддержка светлой/темной темы, 3 требуемых функции.*
✅ **Выполнено:** В React-клиенте сделаны 3 панели. Хэш-генерация написана на стороне клиента без отправки на сервер. Кнопка "📋" копирует значения в буфер обмена. State-manager опирается на `localStorage`.
